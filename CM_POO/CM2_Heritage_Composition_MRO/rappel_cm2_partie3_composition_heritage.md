# Les 3 notions clés : Composition vs Héritage

## 1. "Is-a" vs "Has-a"

La distinction entre les relations "Is-a" (est-un) et "Has-a" (a-un) est fondamentale pour choisir entre héritage et composition dans la modélisation orientée objet. La relation **"Is-a"** représente une spécialisation où la classe dérivée est un type spécifique de la classe parente (un `Chien` **est-un** `Animal`, une `VoitureElectrique` **est-une** `Voiture`), justifiant l'utilisation de l'héritage pour capturer cette taxonomie naturelle et permettre le polymorphisme. La relation **"Has-a"** représente une composition où un objet contient ou utilise un autre objet comme partie de son état interne (une `Voiture` **a-un** `Moteur`, un `Joueur` **a-une** `Arme`), privilégiant la composition pour assembler des fonctionnalités sans créer de hiérarchie artificielle. Le test linguistique est simple : si vous pouvez dire naturellement "X est un Y" alors l'héritage est approprié, mais si vous dites "X a un Y" ou "X utilise un Y" alors la composition est préférable. Une erreur fréquente est d'utiliser l'héritage uniquement pour réutiliser du code (un `Stack` héritant de `List` par commodité) au lieu de modéliser une vraie relation de spécialisation, créant ainsi des couplages inappropriés et violant le principe de substitution de Liskov.

## 2. Avantages de la composition

La composition offre plusieurs avantages décisifs qui en font souvent un choix plus robuste que l'héritage, suivant le principe "favorisez la composition sur l'héritage" popularisé par le Gang of Four. **Flexibilité** : les relations de composition peuvent être modifiées dynamiquement à l'exécution (changer le moteur d'une voiture) alors que l'héritage est figé à la compilation. **Encapsulation** : la composition respecte mieux l'encapsulation en gardant les détails d'implémentation privés, tandis que l'héritage expose les méthodes protégées et crée un couplage fort entre parent et enfant. **Réutilisabilité** : un même composant peut être réutilisé dans des contextes complètement différents sans contrainte hiérarchique, et vous pouvez combiner plusieurs composants indépendants là où l'héritage multiple devient rapidement complexe. **Testabilité** : les dépendances par composition peuvent facilement être remplacées par des mocks ou stubs pour les tests unitaires, alors que l'héritage rend le code plus difficile à tester isolément. **Évolutivité** : modifier une classe composée (ajouter/retirer des composants) est moins risqué que modifier une classe de base dont héritent de nombreuses sous-classes, respectant ainsi le principe ouvert/fermé et réduisant les effets de bord imprévus.

## 3. Quand choisir l'un ou l'autre

Choisissez **l'héritage** quand vous avez une vraie relation de spécialisation "est-un" où la sous-classe est réellement un type spécifique du parent et peut être substituée partout où le parent est attendu (principe de Liskov), quand vous voulez exploiter le polymorphisme pour traiter différents objets via une interface commune, quand la hiérarchie est stable et peu susceptible de changer fréquemment, ou quand vous étendez des frameworks qui utilisent l'héritage comme mécanisme d'extension (Django models, frameworks de tests). Choisissez **la composition** quand la relation est "a-un" ou "utilise-un", quand vous voulez assembler des fonctionnalités de sources multiples sans créer de hiérarchie complexe, quand vous avez besoin de flexibilité pour changer les composants à l'exécution, quand vous privilégiez un couplage faible et une meilleure testabilité, ou quand l'héritage créerait une taxonomie artificielle uniquement pour réutiliser du code. **En pratique**, commencez toujours par la composition comme choix par défaut, et n'utilisez l'héritage que lorsqu'il modélise clairement une relation de spécialisation naturelle du domaine - si vous hésitez, c'est probablement que la composition est plus appropriée. Souvent, la meilleure solution combine les deux : une hiérarchie d'héritage simple pour capturer la taxonomie de base, avec de la composition à l'intérieur des classes pour assembler les fonctionnalités complexes.
