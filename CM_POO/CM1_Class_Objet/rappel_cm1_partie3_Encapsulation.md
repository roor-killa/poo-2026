# Les 3 notions clés de l'encapsulation en Python

## 1. Public, protégé (_), privé (__)

Python utilise des **conventions de nommage** plutôt que des modificateurs d'accès stricts pour gérer la visibilité des attributs et méthodes, reflétant sa philosophie "nous sommes tous des adultes consentants" qui fait confiance aux développeurs. Les **attributs publics** (`nom`, `calculer()`) sont accessibles partout sans restriction, constituant l'interface officielle de la classe destinée aux utilisateurs externes. Les **attributs protégés** préfixés d'un underscore (`_attribut`, `_methode_interne()`) sont une convention signalant "usage interne seulement" ou "réservé aux sous-classes", mais restent techniquement accessibles de l'extérieur - c'est une marque de respect du contrat implicite entre développeurs. Les **attributs privés** avec double underscore (`__attribut`) déclenchent le "name mangling" où Python renomme automatiquement l'attribut en `_NomClasse__attribut`, rendant l'accès direct depuis l'extérieur plus difficile (mais pas impossible) et évitant les conflits de noms dans les hiérarchies d'héritage complexes.

**Important** : contrairement à Java ou C++ où `private` est réellement inaccessible, Python ne force rien - même `__attribut` reste accessible via `objet._NomClasse__attribut`. Le name mangling existe principalement pour éviter les collisions accidentelles de noms entre classe parent et enfant, pas pour une vraie sécurité. La philosophie Python privilégie la documentation et les conventions (`_protected`) sur l'enforcement strict, partant du principe que si un développeur a vraiment besoin d'accéder à un attribut interne, il peut le faire en connaissance de cause. En pratique, utilisez les attributs publics pour votre API, `_protected` pour les détails d'implémentation qui peuvent être utiles aux sous-classes, et `__private` uniquement pour éviter les conflits de noms dans l'héritage multiple ou les frameworks complexes.

## 2. Properties et getters/setters

Les **properties** sont le mécanisme pythonique pour créer des attributs gérés qui ressemblent à de simples attributs publics en syntaxe (`objet.nom`) mais exécutent en réalité des méthodes (getters/setters) en coulisses, permettant de valider, transformer ou calculer des valeurs tout en préservant une interface simple. Le décorateur `@property` transforme une méthode en getter (lecture), tandis que `@attribut.setter` crée le setter (écriture) et `@attribut.deleter` gère la suppression. Cette approche suit le principe pythonique "simple d'abord" : commencez avec des attributs publics simples (`self.nom = nom`), et si vous avez besoin plus tard de validation ou de logique, transformez-les en properties sans changer l'interface utilisée par le code client.

**Syntaxe et utilisation** : définissez un getter avec `@property` au-dessus d'une méthode qui retourne la valeur, puis un setter avec `@nom_attribut.setter` pour contrôler l'assignation. Par exemple, une property `age` peut valider que la valeur est positive, une property `nom_complet` peut calculer dynamiquement à partir de `prenom` et `nom`, et une property `temperature_celsius` peut synchroniser automatiquement avec `temperature_fahrenheit`. Les properties permettent aussi de créer des attributs en lecture seule (getter sans setter), de logger les accès, de déclencher des événements lors des modifications, ou de gérer la lazy initialization (calcul à la première lecture seulement).

**Avantage sur les getters/setters explicites** : contrairement à Java où vous écrivez `obj.getNom()` et `obj.setNom(valeur)`, Python avec properties garde la syntaxe naturelle `obj.nom` et `obj.nom = valeur`, rendant le code plus lisible et permettant d'ajouter de la logique sans casser le code existant - un attribut simple peut devenir une property transparente sans que les utilisateurs de la classe ne changent une ligne de code.

## 3. Validation des données

La validation des données dans l'encapsulation garantit l'intégrité de l'état interne des objets en refusant ou corrigeant les valeurs invalides avant qu'elles ne corrompent l'objet, prévenant ainsi les bugs difficiles à tracer et maintenant les invariants de la classe. **Dans `__init__`**, validez les paramètres immédiatement à la création pour rejeter les objets mal formés dès le départ avec des exceptions explicites (`ValueError`, `TypeError`), évitant qu'un objet existe dans un état incohérent. **Avec properties**, le setter est l'endroit idéal pour valider toute modification ultérieure d'attribut, centralisant la logique de validation en un seul point réutilisé à chaque assignation.

**Techniques de validation** : vérifications de type (`isinstance(valeur, int)`), de plage (`if age < 0: raise ValueError("L'âge doit être positif")`), de format (regex pour email, téléphone), de cohérence entre attributs (`date_fin > date_debut`), ou appel de validateurs externes. Levez des exceptions claires et descriptives plutôt que d'accepter silencieusement des valeurs invalides ou de les corriger automatiquement sans avertir (sauf si c'est explicitement le comportement voulu). Pour des validations complexes, créez des méthodes dédiées (`_valider_email()`, `_valider_coherence()`) appelées par les setters, ou utilisez des bibliothèques comme `pydantic` pour des schémas de validation déclaratifs.

**Pattern défensif** : plutôt que de faire confiance aux utilisateurs de votre classe pour fournir des données valides, adoptez une programmation défensive où chaque point d'entrée (constructeur, setters, méthodes publiques) valide ses inputs. Cela crée une "frontière de confiance" : à l'intérieur de vos méthodes privées, vous pouvez supposer que les données sont valides car elles ont été vérifiées à l'entrée, simplifiant la logique interne et concentrant la gestion d'erreur aux interfaces publiques. La validation fait partie intégrante de l'encapsulation : en contrôlant strictement comment l'état interne est modifié, vous garantissez que votre objet ne peut jamais être dans un état invalide ou incohérent.
